# Проход «выписки ЕГРН → БД → KML + эссе»

**Код:** `parser/egrn_parser/geo_pipeline.py` · **CLI:** `parser/scripts/01e_egrn_pipeline.py`
**Окно:** `parser/gui/egrn_geo_app.py` · **ADR:** [[ADR-007-msk-to-wgs84]] · **Схема:** [[egrn-geometry-8]]
**Контракт KML:** `docs/CONTRACT_KMZ.md` 2.13.0

## Зачем этот проход отдельно от 08_build_kmz

`08_build_kmz` собирает **проект целиком**: фото, документы, граф связей,
бизнес-единицы, бенефициары — и упаковывает в KMZ. Ему нужна заведённая
структура проекта и пройденные шаги 01–07.

Этот проход отвечает на более раннюю задачу: пришла папка выписок, проекта ещё
нет, надо посмотреть что где лежит и отдать результат. Один вход — папка с XML;
три выхода — база, KML, эссе.

```
XML-выписки ──┬─► xml_parser ──────► карточка, права, ограничения  ─┐
              │                                                      ├─► SQLite
              └─► xml_geometry ────► контуры (МСК → WGS-84)         ─┘
                                                                      │
                          ┌───────────────────────────────────────────┤
                          ▼                    ▼                      ▼
                    kml_exporter        essay_md              schema_doc
                    (CONTRACT_KMZ)      (эссе .md)            (описание схемы .md)
```

## Порядок шагов не произволен

Сначала карточка, потом геометрия. Наоборот нельзя: подписи KML и эссе берут
категорию земель, адрес и кадастровую стоимость из `land_objects`, и при
обратном порядке первый прогон дал бы контуры без единой характеристики —
формально верный результат, который человек прочтёт как «в выписке ничего нет».

Карточка пишется через существующий `merge.upsert.save_parsed_result`, и её
падение (например, не установлен `pdfplumber`, который тянет `xml_parser`) не
уносит с собой геометрию: она от этой зависимости не зависит вовсе.

## Четыре формата вывода

| Что | Чем | Кому |
|---|---|---|
| **SQLite** | `xml_geometry_db` + `merge.upsert` | всей системе; §8 — источник для остальных трёх |
| **KML** | `exporters/kml_exporter.py` | на объект, в Google Earth, во вьюер |
| **Эссе `.md`** | `exporters/essay_md.py` | в отчёт, заказчику |
| **Описание схемы `.md`** | `exporters/schema_doc.py` | разработчику, в git рядом с базой |

### KML — что именно соблюдается из контракта

Контрактная поверхность (CONTRACT_KMZ §2) — это KMZ-архив, и одиночный .kml
формально вне её. Но вьюер классифицирует объекты по префиксу `styleUrl` и
разбирает подпись по парам `Ключ: значение; ` — файл, написанный «как удобно»,
через месяц просто не откроется. Поэтому соблюдены все инварианты §6, применимые
к одиночному .kml: префикс `cad_zu_`, уникальный `Style id`, кад.№ отдельным
токеном в `<name>` и ключом в `<description>`, отсутствие HTML, координаты
`lon,lat` с замкнутым кольцом, `kml_schema_version=2.1`, `<atom:author>`,
`graph_node_id` по формуле 04, детерминизм вывода. Каждый пункт — отдельный тест
в `tests/test_kml_exporter.py`.

Сознательное отступление одно: из десяти `<Folder>` создаётся одна,
«Земельные участки». Спека это прямо разрешает (§A.3: «Пустые папки НЕ
создаются»), а больше здесь взяться неоткуда — в §8 только земля.

**ЧЗУ в KML.** Части участка своего класса в контракте не имеют, и это не
упущение: они не объекты учёта. Но для них оставлен суффикс — регулярка кад.№ в
§6 допускает `/N` с подписью «часть/контур». Поэтому ЧЗУ и дополнительные
контуры многоконтурного участка идут отдельными Placemark в той же папке, с
ключом `Часть участка:` вместо `Площадь:` — чтобы площадь части нельзя было
случайно сложить с площадью участка.

### Эссе — почему без LLM

Меморандум по лоту уже пишет `lot_orchestrator` — через модель, с рыночным
анализом. Здесь задача другая: изложить то, что **сказано в выписке**, без
единого слова от себя. Такой текст должен быть воспроизводимым, проверяемым
построчно и не должен уметь ошибаться в цифрах. Модель для этого — лишний риск
без выигрыша: все данные уже разобраны и лежат в таблицах.

Эссе обязано говорить вслух не только факты, но и их качество: сошлась ли
площадь и на сколько, какова заявленная погрешность точек (0.1 м и 2.5 м — это
разные документы), из какой выписки взята каждая цифра. Поэтому раздел
«Границы» стоит раньше раздела «Права»: цифра площади без оговорки о точности
хуже, чем её отсутствие.

Персональные данные правообладателей-физлиц в эссе не попадают никогда — ни
ФИО, ни СНИЛС, ни паспорт. Пишется «Физическое лицо» и вид права: этого
достаточно, чтобы понять обременённость объекта, и недостаточно, чтобы его
разгласить.

### Описание схемы — отпечаток, а не проект

Схема живёт в трёх файлах (канон, миграции, внутренняя схема парсера) плюс
рукописные заметки в `obsidian/Database/`. Четыре источника расходятся не сразу,
а через полгода, и первым это обнаруживает фронт. `schema_doc` снимает описание
**с живой базы**: что в ней фактически есть сейчас. Такой документ не может
врать про существующие таблицы по определению.

Он не заменяет заметки в `obsidian/Database/`: те объясняют **почему** схема
такая (почему §8 отделён от §7, почему площади ЧЗУ нельзя складывать) — этого
из `PRAGMA table_info` не извлечь никогда. Отпечаток отвечает на «что есть»,
заметка — на «почему так».

## Окно (PySide6)

Выбор библиотеки: PySide6 — 65 файлов по репозиториям (EkceloFotoMakeInvent,
VineInvent, project_hub) против 48 у PyQt6. Внешний вид взят из дизайн-кода
EkceloFotoMakeInvent: палитра `BTN_CSS`/`GREEN_CSS`, скругление 6px, вкладки с
номером в заголовке, тяжёлая работа в `QRunnable` + сигналы.

Логики разбора в окне нет ни строчки — всё уходит в `run_pipeline`. Логика,
написанная внутри обработчика кнопки, не тестируется и не переиспользуется, а
этот проход вызывается ещё из CLI и из тестов.

Светофор в таблице результатов использует те же `STATUS_COLORS`, что
EkceloFotoMakeInvent и веб-дашборд: красный `#c0392b` — площадь не сошлась,
охра `#c9a227` — низкая точность съёмки, зелёный `#2e8b57` — норма.

Галка «записывать контур, даже если площадь не сошлась» снята по умолчанию —
это и есть гейт ADR-007 §3 в интерфейсе.

## Запуск

```bash
# консоль
python parser/scripts/01e_egrn_pipeline.py --xml <папка> --db egrn.db --out выгрузка/

# окно
pip install -e parser[gui]
python -m gui.egrn_geo_app        # из каталога parser/
```

## Известное ограничение

`xml_parser.py:771` обрезает текст ограничения до 200 символов
(`_text(content_e)[:200]`). В эссе это видно как оборванная фраза
(«…утверждённых постановлением Правит»). Правка однострочная, но меняет
семантику уже сохранённых данных, поэтому отложена до отдельного решения.
